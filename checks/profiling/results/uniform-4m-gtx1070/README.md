# Uniform 4-million-particle force-evaluation breakdown

Measured on 2026-09-12, NVIDIA GeForce GTX 1070 (8 GiB), driver 580.178.04,
AMD Ryzen 5 3600, 16 GiB host RAM. Upstream source commit:
`47ec34b0d71d3a45cc8913790f84358108308628`.

## Setup and timing method

4,000,000 independent uniform float32 positions in [0,1)^3, seed 0,
equal masses with total mass 1, generated by `jztree_utils.ics.uniform_particles`.
Unmodified `FMMConfig()` defaults: p=5, opening angle 0.8, Plummer softening
0.001, maximum leaf size 32, coarse factor 4, interaction-list allocation
factor 64, Kahan summation off. Complete configuration is in `timings.json`.
The tree has 177,069 / 41,741 / 9,323 / 2,077 nodes in planes 0 / 1 / 2 / 3.
Plane 0 is the finest (leaf-node) plane. Planes are hierarchy groups, not
fixed separation-distance bins: the opening test determines interactions.

The fork's Python sources were loaded using PYTHONPATH, with installed
jzfmm 1.0.1 CUDA 12 extension binaries and jztree 1.1.0, JAX/jaxlib 0.11.1.
The fork's fmm.py is byte-identical to the installed package's fmm.py.
This experiment does not rebuild CUDA binaries from the source commit.

Inputs were resident on the GPU. Four untimed calls per mode exclude JIT
compilation and warm up execution. Thirty individually synchronized wall-clock
samples measure the full force call and the force call on an existing sorted
tree. The latter still builds multipoles and performs the complete interaction
walk and particle evaluation. It excludes sorting/tree construction and
restoring original particle order. Potential and force are computed together.
Both outputs were finite; this is not an independent force-accuracy test.

Ten additional complete force calls were captured with JAX's CUPTI profiler.
The parser uses GPU events, not CPU launch durations. It verifies one serial
compute stream and exactly four M2L/count kernels, four insert kernels, and
one leaf-leaf kernel per call. Dependency-ordered M2L/insert pairs map to
planes 3, 2, 1, 0, as in `_fmm_dual_walk`.

Node2Node totals include the count-array memset, CountInteractionsAndM2L,
intervening prefix scans/list bookkeeping, and InsertInteractions. They exclude
local-to-local shifts; those are in other GPU work, along with sorting/tree
construction, multipole construction, local-to-particle translation, data
movement and output reordering. Host/GPU gaps are the residual between step
wall time and summed GPU event durations. Raw trace files are retained locally
under `/home/bender/Work/benchmarks/jzfmm-planes-2026-09-12/trace`.

## Results

Unprofiled full evaluation: **188.11 ms** median (range 187.71–188.67 ms).

Existing-tree evaluation: **166.31 ms** median.

Profiled full evaluation: **190.01 ms**, 1.0% above the unprofiled median.

| Component | Median GPU time (ms) | % of profiled full call |
|---|---:|---:|
| Near field (leaf-leaf) | 55.46 | 29.2% |
| Node2Node plane 0 | 51.41 | 27.1% |
| Node2Node plane 1 | 18.89 | 9.9% |
| Node2Node plane 2 | 6.59 | 3.5% |
| Node2Node plane 3 | 15.55 | 8.2% |
| Other GPU work | 41.10 | 21.6% |
| Host / GPU gaps | 1.02 | 0.5% |

Individual component medians need not sum exactly to the total median.

| Plane | M2L + count (ms) | Insert kernel (ms) | Remaining list handling (ms) |
|---|---:|---:|---:|
| 0 | 46.38 | 2.60 | 2.44 |
| 1 | 16.33 | 1.16 | 1.40 |
| 2 | 4.77 | 0.64 | 1.18 |
| 3 | 12.03 | 0.64 | 2.88 |

The coarsest plane is not the cheapest. The source deliberately uses a
single-thread-per-receiver mode for the top plane to preserve GPU-count
independence; its interaction pattern also differs. No causal performance
claim about that mode was tested here.

## Implication for cheaper close interactions

Leaf-leaf plus all plane-0 work costs **106.88 ms**. Subtracting that
from the unprofiled timings estimates the following ideal ceilings:

| Assumed cost reduction in those two components | Full call (ms) | Full speedup | Existing-tree call (ms) | Existing-tree speedup |
|---|---:|---:|---:|---:|
| 50% | 134.67 | 1.40× | 112.87 | 1.47× |
| 90% | 91.92 | 2.05× | 70.12 | 2.37× |
| 100% | 81.23 | 2.32× | 59.43 | 2.80× |

These are cost-subtraction projections, not measured accelerated algorithms.
They assume unchanged remaining work and zero replacement overhead at the
100% endpoint. Simply omitting these interactions gives incomplete forces.
Removing only plane-0 M2L arithmetic could not necessarily remove opening
checks or list construction; the 46.38 ms M2L/count kernel combines both.
If only leaf-leaf and that combined kernel became free, the full-call ceiling
would be about 2.18×, rather than 2.32× for the entire plane-0 stage.

The desktop was active and GPU clocks were not locked. This is one particle
seed, one GPU architecture, and one default configuration. Observed ranges
are run variability, not confidence intervals. Timing fractions can differ
on modern GPUs, other distributions, expansion orders and opening angles.

## Reproduce

From the repository root, with a compatible CUDA-enabled jzfmm environment:

```bash
PYTHONPATH="$PWD/src" python checks/profiling/uniform_planes.py --output /tmp/jzfmm-uniform-4m
python checks/profiling/summarize_uniform_planes.py /tmp/jzfmm-uniform-4m
```

The local Python executable was `/home/bender/.venvs/jzfmm/bin/python`.
GPU/CUPTI access is required for the trace. CSV/JSON files retain every timing
sample and the per-plane M2L and insert-kernel measurements.
